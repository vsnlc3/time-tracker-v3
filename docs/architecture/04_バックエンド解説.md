# 04. Backend解説

backendは `backend/spring` のSpring Bootアプリである。パッケージ名は機能単位で分かれており、例えば活動セッション関連は `com.example.springbackend.activity` にまとまっている。

## 1. Backendの層

```text
HTTP request
  -> Controller
  -> Request DTO
  -> Service
  -> Repository
  -> Entity
  -> MySQL
  -> Response DTO
  -> HTTP response
```

この構造の目的は、HTTPの都合、業務ルール、DBアクセスを一つのクラスへ混ぜないことである。

| 層 | 実装例 | 担当 |
| --- | --- | --- |
| Controller | `ActivitySessionController` | URL、HTTP method、path/query/body、status code |
| Request DTO | `StartActivitySessionRequest` | JSON入力の型とBean Validation |
| Service | `ActivitySessionService` | 所有者、重複、区間連続性、トランザクション |
| Repository | `ActivitySessionRepository` | JPAの検索・保存・削除 |
| Entity | `ActivitySession` | DB行に対応する状態と変更メソッド |
| Response DTO | `ActivitySessionResponse` | EntityをAPI公開形式へ変換 |

## 2. Controller

Controllerは `@RestController` であり、基本的には入力を受けてServiceを呼ぶ。

### `ActivitySessionController`

`/api/activity-sessions` を担当する。

| method | API | 呼び出し先 |
| --- | --- | --- |
| GET | `/api/activity-sessions?activityDate=...` | `findByActivityDate()` |
| GET | `/api/activity-sessions/active` | `findActive()` |
| POST | `/api/activity-sessions/start` | `start()` |
| POST | `/api/activity-sessions/manual` | `createTimedManual()` |
| POST | `/api/activity-sessions/{sessionId}/finish` | `finish()` |
| POST | `/api/activity-sessions/{sessionId}/switch` | `switchSegment()` |
| PUT | `/api/activity-sessions/{sessionId}` | `update()` |
| DELETE | `/api/activity-sessions/{sessionId}` | `delete()` |

### `SessionSegmentController`

`/api/session-segments/{segmentId}` のPUT/DELETEを担当し、実処理は `ActivitySessionService.updateSegment()` / `deleteSegment()` に委譲する。区間はActivitySessionの一部なので、独立Serviceを作らず、親セッションの整合性ルールと同じServiceにまとめている。

### その他のController

- `TagController`: `/api/tags` の一覧・作成・更新・削除
- `ManualTimeEntryController`: `/api/manual-time-entries` の一覧・作成・更新・削除
- `SummaryController`: `/api/summary?activityDate=...`
- `UserController`: `/api/users/me`
- `AuthController`: `/api/auth/csrf`

Controllerのpath variableには `@Positive`、bodyには `@Valid`、Controllerクラスには `@Validated` が付いている。

## 3. DTO

### Request DTO

DTOはrecordで定義され、JSON入力をEntityへ直接結びつけない。

- `StartActivitySessionRequest`: `tagId`、`activityDate`、初期 `SegmentType`、区間/セッション予定
- `TimedManualSessionRequest`: 時刻付き手動セッションの開始・終了・durationのうち2つ
- `ActivitySessionUpdateRequest`: タグ、活動日、開始/終了、予定値
- `SegmentSwitchRequest`: 次の `segmentType` と予定秒
- `SessionSegmentUpdateRequest`: 区間のtype、開始/終了、予定秒
- `ManualTimeEntryRequest`: 活動日、total/focus/break秒
- `TagRequest`: 表示名とカラーキー

### Response DTO

- `ActivitySessionResponse`: `durationSeconds`、`active`、`segments`を含む
- `SessionSegmentResponse`: 区間ごとの実績時間を含む
- `ManualTimeEntryResponse`: 秒数内訳を含む
- `DailySummaryResponse`: 合計、FOCUS、BREAK、タグ別内訳、セッション、手動記録
- `TagResponse`: `id`、`displayName`、`color`
- `UserResponse`: `id`、`displayName`、`email`

`ActivitySessionResponse.from()` と `SessionSegmentResponse.from()` は、終了時刻がない場合に引数 `now` までの経過秒を計算する。これにより、DBにはまだ終了時刻がない進行中データでも、APIは現在の経過時間を返せる。

## 4. Service

### `ActivitySessionService`

活動セッションとセグメントの中心的な業務ルールを持つ。

- `start()`: ユーザー行をロックし、所有タグ、予定値、時間重複を確認して親と初期区間を作る。
- `createTimedManual()`: `TimedRangeResolver`で時刻範囲を解決し、完了済みの親・区間を作る。
- `finish()`: 開いている区間を1件取得し、親と区間を同じ終了時刻で閉じる。
- `switchSegment()`: 現区間を閉じ、次の区間を隣接時刻で作る。
- `update()`: タグ、活動日、親の時刻や予定を更新し、最初と最後の区間の境界も調整する。
- `updateSegment()`: 区間更新に合わせ、直前・直後の区間や親の境界を更新する。
- `deleteSegment()`: 区間を削除し、隣接区間をつなぐ。区間が1件だけの場合は拒否する。
- `assertNoOverlap()`: 同一ユーザーの全セッションを対象に実時間の重複を確認する。
- `validateSegments()`: 区間のソート、隣接、親範囲内、open区間の位置を確認する。

`lockCurrentUser()` は `CurrentUserService.requireCurrentUser()` で認証ユーザーを求めた後、`UserRepository.findByIdForUpdate()` を呼ぶ。開始、終了、切り替え、時刻更新など、同じユーザーの時間状態を変更する処理を直列化する意図である。

### `TagService`

- `findAllForCurrentUser()` は初回だけ `ensureDefaultTags()` を実行する。
- `create()` / `update()` は名前をtrimし、同一ユーザー内の重複名とカラーキーを検証する。
- `delete()` は使用中タグと最後の1タグを削除できないようにする。

### `ManualTimeEntryService`

- `create()` / `update()` / `delete()` はタグと記録を同じユーザーのものに限定する。
- `validateBreakdown()` は `totalSeconds == focusSeconds + breakSeconds` を確認する。

### `SummaryService`

`find(activityDate)` は対象日と所有ユーザーでセッション・手動記録を検索し、`TagAccumulator`へタグ別に加算する。活動セッションの合計は親のduration、FOCUS/BREAK内訳は子セグメントのdurationから計算する。

## 5. Repository

RepositoryはSpring Data JPAのインターフェースで、メソッド名から検索条件を作る。

例:

- `ActivitySessionRepository.findAllByActivityDateAndTag_User_IdOrderByStartedAtAsc()`
- `ActivitySessionRepository.findByIdAndTag_User_Id()`
- `ActivitySessionRepository.findFirstByTag_User_IdAndEndedAtIsNullOrderByStartedAtAsc()`
- `SessionSegmentRepository.findByIdAndActivitySession_Tag_User_Id()`
- `ManualTimeEntryRepository.findByIdAndTag_User_Id()`
- `TagRepository.existsByUser_IdAndDisplayName()`
- `UserRepository.findByGoogleSubject()`

`...Tag_User_Id` のように関連EntityをたどってユーザーID条件をRepository queryへ含めることで、ServiceがIDを取得してから別途所有者を確認するだけにならないようにしている。別ユーザーのIDを渡した場合は対象が見つからず、`ResourceNotFoundException` になる。

`@EntityGraph(attributePaths = "tag")` が付いたRepositoryメソッドは、一覧・取得時にタグも取得してResponse DTOのタグ名を利用できるようにするために使われている。

## 6. Entity

Entityは `jakarta.persistence.Entity` でDBテーブルに対応する。

- `User` -> `users`
- `Tag` -> `tags`
- `ActivitySession` -> `activity_sessions`
- `SessionSegment` -> `session_segments`
- `ManualTimeEntry` -> `manual_time_entries`

関連は、多くが `@ManyToOne(fetch = FetchType.LAZY, optional = false)` で表現される。Entityのpublicな変更メソッドは、例えば `ActivitySession.finish()`、`ActivitySession.update()`、`SessionSegment.end()`、`SessionSegment.startAt()`、`Tag.update()` のように、Serviceから状態変更を行うための小さな操作になっている。

EntityをControllerから直接返さず、Response DTOへ変換することで、JPAのlazy relationや内部カラムをAPIへ漏らさない構成になっている。

## 7. Transaction

`ActivitySessionService`、`TagService`、`ManualTimeEntryService` の書き込み処理には `@Transactional` が付く。読み取り専用の一覧処理には `@Transactional(readOnly = true)` が付く。

特にセッション終了では、次の更新を一つのトランザクションにする必要がある。

```text
ActivitySession.finish(endedAt)
SessionSegment.end(endedAt)
validateSegments()
```

途中で失敗した場合に親だけ終了、子だけ未終了という状態を残さないためである。

現行実装では `ActivitySessionService` の主要な時間変更でユーザー行を悲観ロックする。一方、タグ・手動記録のServiceには同じロック処理はない。これは現在のMVPの実装範囲として理解する。

## 8. Validation

検証は3段階ある。

### DTOのBean Validation

- `@NotNull`: 必須ID、日付、enum、開始時刻
- `@Positive`: ID、予定秒、duration
- `@PositiveOrZero`: FOCUS/BREAK秒
- `@NotBlank` / `@Size`: タグ名・カラーキー

### Serviceの業務検証

- `TimedRangeResolver.resolve()`: 時刻3パターンのどれかを要求
- `ActivitySessionService.validateSessionValues()`: 終了>開始、予定値の排他
- `validateSegments()`: 区間の隙間・重複・親範囲外を拒否
- `assertNoOverlap()`: 同一ユーザーのセッション重複を拒否
- `TagService.normalizeColor()`: 許可カラーを限定
- `ManualTimeEntryService.validateBreakdown()`: 秒数内訳を確認

### DB制約

`schema.sql` のNOT NULL、FK、UNIQUE、CHECKが最後の防波堤になる。例えばDBのCHECKは `ended_at > started_at` や `total_seconds = focus_seconds + break_seconds` を保証するが、「同一ユーザーのセッション同士」の比較はDBの単一行CHECKでは表せないため、Serviceの `assertNoOverlap()` が担当する。

## 9. 例外処理

`GlobalExceptionHandler` は `@RestControllerAdvice` である。

- 入力不正、Bean Validation、JSON形式不正、DB整合性違反 -> 400 `ApiError("Request is invalid")`
- `ConflictException` -> 409
- `ResourceNotFoundException` -> 404
- `UnauthorizedException` -> 401
- その他の予期しない例外 -> 500の汎用メッセージ

APIでは例外メッセージやスタックトレースをそのまま返さない。業務上ユーザーへ伝えてよい競合・Not FoundだけService側のメッセージをResponseへ出す。

## 10. Spring Boot設定

`application.properties` では次を設定している。

- `spring.jpa.hibernate.ddl-auto=none`: Entityから勝手にschemaを変更しない
- `spring.sql.init.mode=always` と `spring.sql.init.schema-locations=classpath:db/schema.sql`: 起動時にschema.sqlを実行する
- `spring.jpa.open-in-view=false`: WebレスポンスまでJPAセッションを引き延ばさない
- `spring.jpa.properties.hibernate.jdbc.time_zone=UTC`: JDBC上の時刻基準をUTCにする
- `spring.jackson.deserialization.fail-on-unknown-properties=true`: API bodyの未知フィールドを黙って無視しない
- `server.servlet.session.*`: セッション有効期限、Cookie名、HttpOnly、Secure、SameSite
