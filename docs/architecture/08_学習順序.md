## 2. コードを読む順序

### frontendの最短ルート

```text
app/page.tsx
  -> components/app-shell.tsx
  -> lib/store.tsx
  -> lib/api.ts
  -> components/timer-panel.tsx
  -> components/start-form.tsx / active-session.tsx
  -> lib/time.ts
```

最初に `StoreProvider` を読むと、画面Componentが直接fetchしていないこと、`useStore()`から操作関数を受け取っていることが分かる。次に `api.ts` を読むと、各操作がどのHTTP APIに対応するか分かる。

### backendの最短ルート

```text
ActivitySessionController.java
  -> ActivitySessionService.java
  -> ActivitySessionRepository.java
  -> ActivitySession.java / SessionSegment.java
  -> schema.sql
```

最初の題材はセッション開始がよい。ControllerからService、Repository、Entity、DBまで一通り通るためである。次に `switchSegment()` と `finish()` を読むと、区間の連続性とTransactionの意味が分かる。

## 3. 実際に行うとよい追跡演習

### 演習1: セッションを開始する

次の順に、引数と戻り値をメモしながら読む。

1. `StartForm.handleStart()`
2. `StoreProvider.startSession()`
3. `startActivitySession()`
4. `ActivitySessionController.start()`
5. `ActivitySessionService.start()`
6. `ActivitySessionRepository.save()` と `SessionSegmentRepository.save()`
7. `ActivitySessionResponse.from()`
8. `runMutation()` -> `refreshAll()` -> `toSession()`
9. `TimerPanel` の `activeSession` 判定

ここで、画面の分は秒へ変換され、APIの数値IDはUIの文字列IDへ変換されることを確認する。

### 演習2: FOCUSからBREAKへ切り替える

`ActiveSession.handleSwitch()`、`StoreProvider.switchSegment()`、`ActivitySessionService.switchSegment()`を比較する。

- frontendは次の種類と予定分を送る。
- backendは現在区間を終了し、次の区間を同じ時刻から開始する。
- `validateSegments()`が隙間と重複をチェックする。
- frontendはmutation後に再取得する。

### 演習3: ページ再読み込み

`StoreProvider`の初期`useEffect`、`getCsrfToken()`、`getCurrentUser()`、`refreshAll()`、`toSession()`、`activeSession`を読む。

重要なのは、タイマーの経過時間自体を保存しているのではなく、DBの `startedAt` とブラウザの `now` から毎回計算している点である。

### 演習4: 日付と時刻を比較する

`ManualEntryDialog`、`timeStrToEpoch()`、`TimedRangeResolver.resolve()`、`ActivitySessionService.assertNoOverlap()`、`TodaySummary`、`RecordsView`を読む。

- `activityDate`は集計対象日の値。
- `startedAt` / `endedAt`は実時間の値。
- overlapは実時間で判定する。
- summaryとrecordsのグループ化は`activityDate`で行う。

この2種類の日付を混同すると、日跨ぎの手動入力やサマリーを誤って理解する。

## 4. 現行実装と目標方針の読み分け

`docs/開発ガイドライン.md` は目標として次を挙げている。

- Zustand
- React Hook Form
- TanStack Query（React Query）
- SWR
- localStorage

しかし、現行frontendの実コードでは次を使っている。

- Zustandではなく `StoreContext` / `StoreProvider` / `useStore()`
- React Hook FormではなくComponentの `useState`
- TanStack Query / SWRではなく `lib/api.ts`、`refreshAll()`、`runMutation()`、15秒polling
- 業務データ保存はlocalStorageではなくSpring Boot APIとMySQL

したがって、ライブラリ名だけを見て「導入済み」と判断しない。`package.json`、import、`StoreProvider`の実装を確認する。

## 5. 理解が難しいポイント

### 1. ActivitySessionとSessionSegmentの二重構造

親は活動全体、子はFOCUS/BREAKの連続区間である。切り替え・編集・終了では両方の境界を合わせる必要があり、`validateSegments()`が多くのルールを持つ。

### 2. server stateとlocal UI state

タグや記録はサーバーstate、Dialogの開閉や入力途中の値はlocal stateである。`StoreProvider`が両方の操作入口を公開するため、何がDB由来かを意識して読む必要がある。

### 3. JSESSIONIDとCSRF tokenは役割が違う

JSESSIONIDは「どのログインセッションか」を示すHttpOnly Cookie、XSRF-TOKENは「mutationを意図したfrontendか」を確認する値である。後者はJavaScriptが読み、`X-XSRF-TOKEN` headerへ送る。

### 4. 同一オリジンに見えるrewrite

ブラウザの `/spring-api` とDocker内部の `http://backend:8080` は別の場所だが、`next.config.mjs`が中継する。API clientのURLとComposeのservice名を両方見る必要がある。

### 5. DB制約とServiceルールの分担

`total_seconds = focus_seconds + break_seconds`はDB CHECKで守れる。一方、同一ユーザーの別行との時間重複、所有者チェック、区間連続性はServiceで守る。この分担は `schema.sql` と `ActivitySessionService` を並べて読むと分かる。

### 6. backend APIと現行画面の対応範囲

backendには `PUT /api/manual-time-entries/{entryId}` があるが、現行frontendには手動記録編集UIと対応API関数がない。実装を理解するときは、backendにendpointがあることと、画面から到達できることを同じ意味にしない。
