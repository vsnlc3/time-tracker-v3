## 4. インフラ / デプロイ

### 現在実装済み
- FrontendはNext.js、BackendはSpring Boot / Java、DBはMySQLで構成する。
- 開発環境と本番環境はDocker構成を分離する。
  - 開発用：`compose.yaml` と `frontend/nextjs/Dockerfile.dev`
  - 本番用：`compose.prod.yml` と `frontend/nextjs/Dockerfile.prod`
- Docker ComposeでFrontend、Backend、MySQLの3コンテナを起動する。
- 本番FrontendはDockerイメージのビルド時に `pnpm build` を実行し、起動時は `pnpm start` を使用する。
- 本番Backendは既存のSpring Boot用Dockerfileでビルドし、MySQLコンテナとDockerネットワーク内で通信する。
- Frontend、Backend、MySQLはDockerネットワーク内で通信できる。Next.jsのサーバーサイド処理からは `backend:8080` に接続できるが、ブラウザ上のJavaScriptが `backend:8080` や `mysql:3306` へ直接アクセスする構成ではない。
- ブラウザからBackendへアクセスする場合は、Frontendの同一オリジン経由で中継するか、将来的にリバースプロキシを経由する。BackendとMySQLはホストの外部ポートへ公開しない。
- 本番のMySQLデータは本番用の名前付きvolumeに保存する。
- 本番環境変数は `.env.production.example` をテンプレートとして、Lightsail上に `.env` を作成し、実際の値を設定する。`.env` はGitへコミットしない。
- 本番コードはGitHubリポジトリからAWS Lightsailへcloneして配置する。
- AWS Lightsailの構成は以下を前提とする。
  - リージョン：東京
  - OS：Ubuntu 24.04 LTS
  - リソース：2GB RAM / 2vCPU
  - Docker / Docker ComposeをUbuntu上にインストール
- 現在は動作確認を優先し、LightsailのPublic IPv4からFrontendの3000番ポートをHTTPで一時的に公開している。Lightsail FirewallでもTCP 3000を一時的に許可している。
- これは本番完成形ではなく、デプロイ確認用の一時構成である。

### 現在のデプロイ方針
1. LightsailへGitHubリポジトリをcloneする。
2. `.env.production.example` を元にLightsail上で `.env` を作成し、本番環境変数を設定する。
3. `docker compose -f compose.prod.yml up -d --build` でFrontend、Backend、MySQLをビルド・起動する。Docker Composeが同じディレクトリの `.env` を読み込む。
4. まずは手動デプロイを安定させ、動作確認とログ確認を行う。

### 次に対応したい
- Lightsail Static IPを割り当てる。
- 独自ドメインを取得し、DNSを設定する。
- CaddyまたはNginxをリバースプロキシとして導入する。
- 公開構成は、InternetからCaddyを経由し、`/api/*` を `backend:8080`、その他のパスを `frontend:3000` へ転送する形を想定する。
- HTTPSを有効化し、外部公開ポートを80/443へ集約する。
- Static IP、独自ドメイン、Caddy、HTTPSの導入後は、Frontendの3000番ポートの外部公開を停止し、Lightsail FirewallからTCP 3000の許可ルールを削除する。
- リバースプロキシ導入後は、Frontendの3000番、Backendの8080番、MySQLの3306番を外部公開せず、Webアクセスは80/443のみを公開する。
- Lightsail Firewallの許可ポートを必要最小限にする。

### 将来的に学習として取り入れたい
- 現在の1台構成とDocker Composeを維持したまま、デプロイ手順をスクリプト化する。
- CPU、メモリ、ディスク容量を確認し、2GB RAM / 2vCPUの環境に適した構成・運用を学ぶ。
- 現時点ではRDS、ECS、Kubernetesなどのサービスは採用せず、必要性を理解したうえで将来の比較対象とする。

## 5. 運用 / セキュリティ

### 現在実装済み
- DBパスワード、Google OAuth情報、公開URLなどの環境依存値はComposeやアプリケーションコードへ直接書かず、環境変数から注入する。
- Lightsail上の `.env` はGitへコミットせず、サーバー上で安全に管理する。`.env.production.example` は本番環境変数のテンプレートとしてGitで管理する。
- 本番ComposeではBackendとMySQLのホスト公開ポートを設定しない。
- MySQLにはデータ保持のための本番用volumeを使用する。
- 本番Composeではコンテナに `restart: unless-stopped` を設定する。

### 次に対応したい
- HTTPS導入後にSecure Cookieを有効化する。
- Google Cloud Consoleへ本番環境のOAuth Redirect URIを登録し、アプリケーション側の `GOOGLE_REDIRECT_URI` と一致させる。
- MySQLだけでなくBackendとFrontendにもヘルスチェックを追加する。
- Lightsail FirewallでHTTP/HTTPS以外のアクセスを制限する。
- SSHポートのアクセス元を自分の接続元などに制限する。

### 将来的に学習として取り入れたい
- Dockerログの肥大化対策とログローテーションを設定する。
- アプリケーションログを確認しやすい形式・出力先に整理する。
- CPU、メモリ、ディスク使用量の監視方法を整える。
- MySQLデータの定期バックアップと復旧手順を用意する。
- Lightsail Snapshotの取得・復元を試す。
- 不要になったDocker imageや停止済みcontainerを安全に整理する。

## 6. CI/CD

### 現在の状態
- GitHubからLightsailへcloneし、Lightsail上でDocker Composeを使って手動デプロイする。
- CI/CDやContainer Registryはまだ導入していない。

### 導入方針
複雑な構成を最初から導入せず、以下の順番で段階的に進める。

1. GitHub Actionsでテストを実行する。
2. GitHub ActionsでDocker imageをbuildする。
3. Container Registryへimageをpushする。
4. Lightsail上でimageをpullして起動する。
5. 将来的に、`main` ブランチへのpushを起点とした自動デプロイを検討する。

---
## 7. 段階的な実装順

学習用の個人開発として、現在の1台構成を複雑化しすぎないよう、次の順番で対応する。

1. 現在の手動デプロイ、環境変数管理、MySQLデータ保持を安定させる。
2. Lightsail Static IP、独自ドメイン、DNSを設定する。
3. CaddyまたはNginxとHTTPSを導入し、公開ポートを80/443へ集約する。
4. Secure Cookie、OAuth Redirect URI、Firewall、SSHアクセス制限を整える。
5. ヘルスチェック、ログローテーション、バックアップ、Snapshotを追加する。
6. GitHub ActionsでテストとDocker image buildを自動化する。
7. Container Registryとimage pull方式を試し、必要性を確認してから自動デプロイへ進む。
